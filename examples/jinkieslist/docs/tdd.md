## Summary

JinkiesList is a mobile app backed by one API service and one Postgres database.
The app keeps a local copy of the household's list and pantry and works
offline; a sync protocol merges changes when a device reconnects. The key
decision is that list and pantry changes are recorded as operations, not
overwritten states, so concurrent offline edits can be merged without loss
([ADR-0002](#adr-0002)).

## Context and constraints

- Shoppers are often offline in stores ([R-LIST-02](prd.md#r-list-02)), so
  the app never waits on the network to show a change.
- Changes reach other members within 3 seconds
  ([R-LIST-01](prd.md#r-list-01)).
- A two-person team runs it, so the design favours one service and managed
  infrastructure.

## Architecture

The phone app writes every change to its local store and to an outbox.
[T-SYNC](#t-sync) sends the outbox to [T-API](#t-api), which applies the
operations in [T-STORE](#t-store) and pushes them to the household's other
devices over a websocket. [T-PANTRY](#t-pantry) runs inside the API and
reacts to operations that affect the pantry.

```text
phone app ──outbox──▶ T-API ──▶ T-STORE (Postgres)
    ▲                   │
    └──── websocket ◀───┘   T-PANTRY runs inside T-API
```

## Components

<a id="t-sync"></a>
### T-SYNC — Offline sync

- **Responsibility:** keep each device's copy consistent with the server
- **Requirements:** [R-LIST-01](prd.md#r-list-01), [R-LIST-02](prd.md#r-list-02)
- **Depends on:** [T-API](#t-api)
- **Detail:** [tdd/sync.md](tdd/sync.md)

<a id="t-api"></a>
### T-API — API service

- **Responsibility:** authenticate members, apply operations, push changes
- **Requirements:** [R-LIST-03](prd.md#r-list-03)
- **Depends on:** [T-STORE](#t-store)

A single stateless service behind a load balancer. Invitation links are
signed tokens that expire after 7 days; revocation adds the token to a deny
list in [T-STORE](#t-store).

<a id="t-pantry"></a>
### T-PANTRY — Pantry rules

- **Responsibility:** move bought items to the pantry, track expiry, restock staples
- **Requirements:** [R-PANTRY-01](prd.md#r-pantry-01), [R-PANTRY-02](prd.md#r-pantry-02), [R-PANTRY-03](prd.md#r-pantry-03)
- **Depends on:** [T-STORE](#t-store)

When a staple's quantity reaches zero, T-PANTRY adds an item to the list
unless an unchecked item with the same name exists, so a staple is added
once.

<a id="t-store"></a>
### T-STORE — Database

- **Responsibility:** hold households, members, operations, and current state
- **Depends on:** none

## Data model

| Table | Holds | Key |
|---|---|---|
| `household` | name, created date | `id` |
| `member` | household, display name, role | `id` |
| `operation` | household, device, sequence, kind, payload | `(device_id, seq)` |
| `item` | current list state, derived from operations | `id` |
| `pantry_entry` | current pantry state, derived from operations | `id` |

## Failure modes

| Failure | Effect | Handling |
|---|---|---|
| Websocket drops | Other members' changes stop arriving | The app polls every 30 seconds until it reconnects |
| Database unavailable | Operations cannot be applied | The API returns 503; devices keep them in the outbox |

## Rollout and rollback

Every schema change is additive for one release before anything is removed,
so the previous app version keeps working during a rollback.

## Decision records

<a id="adr-0003"></a>
### ADR-0003 — Invitation links are signed tokens

- **Status:** accepted
- **Date:** 2026-08-14

**Context.** Invitations must work for people who have no account yet.
**Decision.** An invitation is a signed token carrying the household and an
expiry. **Alternatives.** Emailed codes, rejected because many households
share by chat. **Consequences.** Revocation needs a deny list.

<a id="adr-0002"></a>
### ADR-0002 — Record changes as operations and merge them

- **Status:** accepted
- **Date:** 2026-08-05
- **Supersedes:** [ADR-0001](#adr-0001)

**Context.** Offline edits made on two devices collided, and last-write-wins
lost one of them. **Decision.** Every change is an operation with a device
sequence number; the server applies operations in order and flags true
conflicts for the member to resolve. **Alternatives.** A CRDT library,
rejected as more than the list needs. **Consequences.** The server keeps an
operation log, compacted after 30 days.

<a id="adr-0001"></a>
### ADR-0001 — Last write wins

- **Status:** superseded
- **Date:** 2026-07-20
- **Superseded by:** [ADR-0002](#adr-0002)

**Decision.** The newest version of an item replaced older ones.
